## 優先度の高い指摘

### 1. HIGH：通信量が4 GiBで折り返す

場所：`Sources/CoreSampler.swift:577`（取得）、同ファイル399–411（速度計算）。

`getifaddrs`のAF_LINK情報を`if_data`として読み出している。対象macOS SDKの`net/if_var.h`で、`ifi_ibytes`・`ifi_obytes`は32bit符号なし整数。取得後にUInt64へ変換しても、元のカウンタの折り返しは解消されない。

各インターフェースの通信量が4 GiB境界を超えると、累積値が小さな値へ戻る。速度計算もカウンタ減少として欠測になり、高速通信では計測間隔内の複数回の折り返しも扱えない。

修正方向：`NET_RT_IFLIST2` / `if_msghdr2`等の64bit統計取得へ変更し、4 GiBをまたぐ累積値と速度の回帰テストを追加する。

確度：高。SDK型定義とコードの照合による。実際に4 GiBの通信を発生させる試験は行っていない。

### 2. HIGH / 設計BLOCK：大規模ファイル走査で全件処理とコピーを反復する

場所：`Sources/StorageScanner.swift:343`、377–392、64–69、`Sources/App.swift:277`、`Sources/MonitorStore.swift:85`。

約0.3秒ごとの進捗通知で、全ノードを集計し、全配列を状態に格納してメインスレッドへ渡す。その状態が配列を保持している間に走査側が次の項目を追加すると、Swiftのcopy-on-writeで配列全体の複製が必要になる。表示側も子フォルダ一覧を求めるたびに全ノードをfilterする。走査中のノード数には上限がなく、読み込み時の200万件制限は走査そのものを制限しない。

ファイル数が多いほどCPU・メモリ・画面更新の負荷が増える設計で、軽量な監視と全起動ボリューム走査の両立に問題がある。

修正方向：進捗通知は件数・合計サイズ・エラー差分を中心にする。ツリーは増分更新、ページ単位の取得、明示更新等で渡し、親IDから子一覧を得る索引を用意する。保存結果の読み込みもメインスレッド外で行う。

確度：全件処理・コピーの発生は高。実ディスク全体の所要時間やUI停止時間は未測定。

設計担当の10万ノード合成データによる最適化ビルドでの観測値：

| 処理 | 測定結果 |
|---|---:|
| 古いスナップショットを保持した状態のappendによるコピー | 10回で50.82 ms |
| `children(of:)` | 30回で169.50 ms |
| 全ノードの合計計算 | 30回で137.64 ms |

これは合成データの測定であり、100万件・全ディスクでの絶対時間へは外挿しない。設計BLOCKは、主要機能である大規模走査に対してこの反復処理と保持量の制御が不足していることに基づく。

## 中程度の指摘

### 3. MEDIUM：キャンセル前に予約された追加計測が後から開始できる

場所：`Sources/AdditionalCollectors.swift:33`、47、`Sources/MonitorStore.swift:238`、251、265。

追加計測はバックグラウンドキューへ予約される。実行開始前に一時停止・終了処理が`cancel()`を呼んでも、後から始まった`run()`がキャンセルフラグをfalseへ戻す。そのため、キャンセル後に予約済みのnettopやpowermetricsが起動する実行順序が存在する。管理者計測の場合は認証を伴う処理も対象になる。

修正方向：計測予約時の世代トークンを実行開始時に検査し、終了済み状態を解除しない。実行中のプロセス停止だけでなく、開始前のキャンセルを検証するテストを追加する。

確度：コード上の競合経路は高。設計担当の隔離確認では、cancel後に予約処理相当の`/bin/sleep 1`を開始すると約1.011秒完走した。アプリ終了後に認証画面が残る等の具体的なUI挙動は未実証。

### 4. MEDIUM：通常のスリープ復帰でスリープ時間の計測基準を消している

場所：`Sources/MonitorStore.swift:89`、109、`Sources/CoreSampler.swift:81`、351。

スリープ前にpause、復帰時にstartするが、start内の`CoreSampler.reset()`が`previousClock`を消す。そのため、スリープ前後の時計差から時間を求めるはずの処理が、通常の復帰時には「初回計測待ち」になり、スリープをまたいだ値を得られない。

修正方向：CPU・I/O用の基準と時計用の基準を分ける。CPU速度等の欠測区間は維持しつつ、時計だけはスリープ前後を比較できるようにする。

確度：高。通知からresetまでの呼び出し経路による。実スリープの再現試験は行っていない。

### 5. MEDIUM：ディスクI/Oエラーの未取得を「実測0件」にしている

場所：`Sources/CoreSampler.swift:603`、433。

読み書きバイト数が得られた場合、`Errors (Read)`または`Errors (Write)`の欠損を`?? 0`で埋め、合計を実測として表示する。「取得できなかった」と「エラーがなかった」を区別できていない。

修正方向：エラーカウンタの有無を保持し、両方欠損なら取得不可、片方欠損なら部分取得として表示する。カウンタ欠損のテストを追加する。

確度：高。欠損時のコード分岐による。検証機でこのフィールドが実際に欠損していたという指摘ではない。

### 6. MEDIUM：指標ごとの欠測区間を履歴グラフが線でつなぐ

場所：`Sources/App.swift:214`、229、`Sources/History.swift:47`。

ある指標が一時的に取れなくても、ほかの指標があれば履歴フレームは保存される。グラフは対象指標がないフレームを除外し、残った前後の点を同じsegmentの線でつなぐ。したがって、一時停止・再開の区間は分かれていても、個別の取得失敗による欠測は線で補間される。「欠測は接続しません」という表示と一致しない。

修正方向：指標ごとに欠損または時間の空白を検出し、線の区間を分割する。値あり→欠損→復帰のチャート入力をテストする。

確度：高。グラフ用データの抽出とseries指定による。以前の実画面検証は、この個別欠測のケースを確認したものではなかった。

## 設計上のWATCH

### 7. 履歴の全件整理を基本監視のたびにメインスレッドで繰り返す

場所：`Sources/MonitorStore.swift:158`、`Sources/History.swift:27`、41、55。

各基本サンプルでpruneし、append内部でもpruneする。pruneは全フレーム内の辞書filterとソートを行う。24時間分8,640フレーム×40値の合成データで、通常のprune＋append経路は30回平均25.32 msだった。新規収録や保存時には追加の整理も実行される。

直ちにフリーズするとまでは判断しないが、1秒監視や大規模走査と重なると画面応答を圧迫する。読み込み時の検証と通常の期限切れ削除を分け、同じ周期の重複整理を避けることを推奨する。

### 8. 収集層が数値画面の表・ラベルを直接生成している

場所：`Sources/Common.swift:55`、`Sources/DeviceSampler.swift:17`、`Sources/MonitorStore.swift:27`。

収集結果の共通モデルに日本語ラベル・表列・列幅を含め、collectorが直接生成する。初期数値画面には実用的だが、将来の相棒UIは数値画面向けモデルに依存するか、意味のある観測値をそこから取り出す必要がある。

修正方向：値・単位・状態・取得元・安定した指標IDを観測モデルとし、ラベルや列幅を表示側で付ける。初期版の機能不良としては数えず、キャラクターUI着手前の設計課題として扱う。
