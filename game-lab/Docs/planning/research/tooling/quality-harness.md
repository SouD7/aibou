# aibouゲーム開発：操作・観測・検証のためのツール構成

調査日：2026-09-14  
対象：自作aibouのCPU・メモリ・回路などのミニゲーム。既存作品の内部APIやメモリを調査・改変する提案ではない。  
位置づけ：公式文書で機能を確認した設計提案。導入、実装、比較ベンチマークは未実施。

## 結論

品質を重視するなら、**computer useによるプレイと、自作ゲームに用意する検証用の窓口を組み合わせる**。AIが画面を見て操作するだけでなく、「同じ状態からやり直す」「一手ずつ進める」「何が起きたかを値として確認する」「失敗を再現する」ことができる開発環境が必要である。

既存のaibouにはSwiftによるmacOS実装があるため、まずは **既存のcomputer use + Swiftのロジックテスト + XCTest/XCUIAutomation + Instruments + 小さな自作検証窓口** が最小の候補になる。Webでゲームを実装すると決めた場合は、UIテストをPlaywrightに置き換える。Godotはゲームの要求から採用する選択肢であり、AI操作のためだけに追加する必要までは確認できない。

特定のエンジンのほうが楽しいゲームになる、またはAIが高品質に実装できるという比較結果はない。ツールの数を増やすことより、学習内容・画面・実際の操作の対応を再現可能に検証することを優先する。

## computer useだけでは不足する理由

| 確認したいこと | 画面操作で得られるもの | 追加で必要になるもの |
|---|---|---|
| ワイヤーを接続したらランプが点く | 操作できたことと見た目 | 入力・配線・論理値・出力の記録、真理値表との一致 |
| CPUの仕事が流れている | 動き、説明の読みやすさ | 命令位置、レジスタ、待ち時間、実行済み仕事の値 |
| RAM容量を変えると結果が変わる | 実験として違いが見えること | 同じ仕事量・入力条件からの比較、ゲーム内RAMと保存先の区別 |
| 引っかかりなく動く | 主観的な滑らかさ | 実際のフレーム時間、CPU/GPU負荷、メモリの継続的な計測 |
| 学べた・楽しかった | AIによるレビュー仮説 | 想定利用者による初見プレイと、未経験の条件についての説明・予想 |

これはcomputer useの劣等性ではなく、画面からわかることと内部モデルから検証できることが異なるためである。特にCanvasは、そのままでは描かれた物体を意味を持つUI要素として提供しない。Playwrightのようなブラウザ自動化を用意しても、回路の端子・データ箱・作業者の意味を自動的に理解できるわけではない。[MDN：canvasのアクセシビリティ](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas#accessibility)

## 自作ゲームに最初から用意する「検証用の窓口」

以下は既製の万能MCPの紹介ではなく、aibou側に設計する小さなインターフェース案である。最初からMCPサーバーにする必要はなく、テストから呼べる関数やローカルのCLIでよい。ゲームの通常ロジックと同じ処理を通す。

| 機能案 | 受け渡すもの | 得られる品質 |
|---|---|---|
| `loadScenario / reset` | 問題ID、乱数seed、初期条件、モデル版 | 同じ問題・条件から繰り返せる。リトライで原因が変わらない |
| `observe` | 現在の問題・tick・入力・配置・仕事待ち行列・数値・成否 | 「ゲームが何を計算しているか」を画面と照合できる |
| `step` | 1命令、1クロック、一定数のシミュレーションtick | 時間を止めて因果を追い、条件の境界を確かめられる |
| `dispatch` | 「入力AをON」「端子AとBをつなぐ」等の意味を持つ操作 | 大量の条件確認や、短い操作記録からの再現ができる |
| `record / replay` | 初期状態＋tick付き操作列＋モデル版＋seed | 不具合報告に「この再現ファイルで起きる」を添えられる |
| `capture` | 現在の状態と対応するスクリーンショット、短い録画 | 見た目と値が対応し、修正前後を比較できる |
| `metrics` | フレーム時間、更新時間、実アプリのメモリ、エラー | 重くなる場面を再現ファイルと結びつけて調べられる |

`observe`はゲーム内の教育用シミュレーション状態を読む。実OSのプロセス情報やユーザーの作業データは、この検証窓口に必要ない。画面の「電源OFF」「メモリを減らす」は仮想PCのモデルに対する操作とする。

乱数seedだけで完全な再現性が得られるとは限らない。時間刻み、イベントの順序、外部入力、初期保存データ、エンジンやモデルの版も揃える。Phaserにはseed付き乱数生成器があり、Godotには乱数のseedと状態を保存・復元する機能があるが、これらはゲーム全体の再現性を代行する機能ではない。Godotは基礎アルゴリズムを実装詳細としているため、長期のreplayには版情報も残す。[Phaser：RandomDataGenerator](https://docs.phaser.io/phaser/concepts/math#randomdatagenerator)、[Godot：RandomNumberGenerator](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)

### 操作できた証拠と、内部で正しかった証拠を分ける

- **UIの通し確認**：本番と同じ画面をクリック・ドラッグ・キー操作し、開始、試行錯誤、成功、失敗、リセットまで遊べることを確認する。状態を直接書き換えてクリアしても、この確認の代わりにはならない。
- **ロジックの確認**：検証用窓口から条件を固定し、多数の入力・境界条件・再現手順を確認する。画面では見えにくい誤りを見つける。
- **両者の対応確認**：UIで行った一手が記録にどう残り、値と表示をどう変えたかを照合する。

`dispatch`がUIのイベントを飛ばしてモデルを操作する経路は、モデルの検証に使う。UI入力検証の成功として扱わない。通常のボタンにはアクセシビリティ情報を付け、Canvas/SpriteKitの独自描画には必要な名前・状態・操作手段を補う。

## 実装方式ごとの候補

| 実装方式 | 操作・回帰確認 | 原因調査・計測 | 位置づけ |
|---|---|---|---|
| 既存Swift/macOSを伸ばす | computer use、XCTest/XCUIAutomation、上記の検証窓口 | Xcodeのデバッガ、Instruments、テストへの画像添付 | 既存構成を活かす最小候補 |
| Webゲームを作る | computer use、Playwright Test、上記の検証窓口 | Playwright trace・画像差分、Chrome DevTools Performance | Web採用時の検証環境。Canvasの意味付けは別途必要 |
| Godotで作る | computer use、Godotのヘッドレス実行＋自作シナリオランナー | Remote Scene Tree/Inspector、Profiler、movie出力 | エディタ・シーン制作が必要な場合の候補。独自テスト設計は必要 |

### Swift/macOS

XCTestは条件の検証と性能の回帰計測を扱い、XCUIAutomationと組み合わせて実際のUI操作の流れをテストできる。スクリーンショットは画面やUI要素から取得し、テストの添付資料として残せる。XCTestに画像取得機能があることと、Playwrightのような画像差分運用が自動で完成することは別なので、画像の基準・差分・人のレビュー手順は設計する。[Apple：XCTest](https://developer.apple.com/documentation/xctest)、[Apple：XCUIScreenshot](https://developer.apple.com/documentation/xcuiautomation/xcuiscreenshot)

SpriteKitはmacOSを含むApple環境で2D描画・アニメーション・物理挙動を扱う。CPU・回路・RAMの教育用モデルは、画面描画から分けたSwiftの処理として持つと、1命令ずつの確認や入力全通りの検証をしやすい。これは設計上の提案であり、SpriteKitの自動保証ではない。[Apple：SpriteKit](https://developer.apple.com/documentation/SpriteKit?changes=_7)

InstrumentsのGame Performanceテンプレートは、CPUスレッド・GPU・表示・メモリ等の情報からフレーム時間の問題を調べるための道具である。aibouのモニタ表示だけを使ってaibou自身の軽さを判定せず、外部の計測を併用する。[Apple：Metalアプリの性能分析](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app)

### Web / Phaser等

Playwrightの時計は、日時、タイマー、`requestAnimationFrame`などを制御できる。時間を進めてアニメーションや待ち時間を調べられるが、Web Worker・音声・エンジン独自時計等を含む全実行系が自動で同期するとは仮定しない。学習モデルは専用の`step`を持たせるほうが、1命令・1クロックの意味を明確にできる。`fastForward`は取り逃したタイマーを各1回処理する用途があり、全フレームを積み上げる検証と同一ではない。[Playwright：Clock](https://playwright.dev/docs/clock)

Playwrightの画像比較は基準画像と実行結果の差分確認を提供する。同じOS・ブラウザ・フォント・画面条件で基準を作り、ゲームのseedとtickも揃える。画像一致は「前と同じ」を確かめる仕組みで、初回の画像が美しい・正しいことは人または独立したレビューで確かめる。[Playwright：Visual comparisons](https://playwright.dev/docs/test-snapshots)

Playwright traceは操作・画面・DOM・ログ等をつなげて失敗を調べられる。自作モデルの状態JSONとreplayも同じ試行に添える。DOMの記録からCanvas内部の回路状態を再構築できるとは仮定しない。traceの常時取得には負荷があるため、日常の回帰確認は失敗時保持、体験レビューは対象シナリオを明示して録画するなど用途を分ける。[Playwright：Trace Viewer](https://playwright.dev/docs/trace-viewer)

フレームの問題はChrome DevTools Performanceで時間軸・フレーム・メインスレッド処理から分析する。これはChromiumでの性能確認であり、最終配布がWKWebView等なら、その実際の実行環境でも計測・操作する必要がある。[Chrome：Runtime performance](https://developer.chrome.com/docs/devtools/performance)

### Godot

Godotは実行中のシーンをRemoteで選び、ノードの値を調べたり変更したりできる。Profilerやモニタも標準で提供される。これはデバッグ機能であり、そのままAI向けの意味を持つ操作・学習目標・成否判定を提供するものではない。[Godot：Debugging tools](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/overview_of_debugging_tools.html)

CLIにはヘッドレス実行、スクリプト起動、ログ出力、movie出力、固定FPSなどがある。問題モデルの回帰確認と再現映像の出力に使える。ただしmovie出力で固定FPSを強制して滑らかな映像が得られても、それは実時間に滑らかに動いた証拠にならない。リアルタイム性能は別の計測として扱う。[Godot：Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

## 学習の正確さを確かめるテスト例

以下はaibou向けの確認設計であり、各ツールの既製機能ではない。画面と独立した期待値・真理値表・短い手計算からテストをつくる。実装の出力をそのまま正解データにしない。

| 学習テーマ | 仕組みの確認 | 画面操作で確かめること | 人の理解を確かめる課題 |
|---|---|---|---|
| 論理回路 | 全入力について指定の真理値表と一致。桁上がり・未接続等も仕様どおり | 接続・切断・入力変更が意図どおりでき、何が変わったか読める | 初めての入力に対する出力を、実行前に予想する |
| 記憶する回路 | 書込み許可なしでは保持。許可と更新時点の条件に沿って書き換わる | 記憶した値と現在の入力が見分けられる | 入力を戻しても結果が残る理由を説明する |
| CPU | 命令ごとの状態遷移、分岐、停止を手計算例と照合 | 一時停止・一命令実行で、どこを実行したか追える | 命令を1つ変えた結果を予想する |
| RAMと保存 | 明示した単純化モデルの中で、未保存の状態と保存済み状態を区別 | 編集・保存・仮想電源OFFの違いが見える | 新しい作業例で、容量を増やす場所を理由付きで選ぶ |
| 並列処理 | 依存関係が守られ、同時に処理できない仕事が先行しない | コア数を変えた前後を同じ仕事で比較できる | コア数を増やしても速くなりにくい仕事を見分ける |
| ボトルネック | 条件を固定した比較で、指定モデルの律速と完了時間が対応 | 一箇所を変えた効果と他の待ちが見える | 未経験の仕事量に対して、改善する箇所を予想する |

高度な実CPUの全挙動を再現することと、初心者に必要な因果関係を正しく表すことは異なる。モデルごとに「表す関係」「省略する関係」「この条件の中だけで成立する法則」を制作資料に残し、解説とゲームのルールを照合する。

## 楽しさと学習効果の確認

自動テストは、クリア可能性、状態の整合、回帰、再現性を確かめる。AIによるプレイは、説明不足・迷いやすさ・操作の不自然さについて改善仮説を出す。想定する初心者が学べるかは、人による初見プレイで確かめる。

最初の試作では、各ゲームについて次を観察する設計を推奨する。

1. 最初に何をしてよいか、説明を補わずに理解できるか。
2. 誤った予想をしたあと、結果から理由を考えて次の操作を変えられるか。
3. 一度クリアしたあと、条件を変えて自発的にもう一度試したくなるか。
4. 遊ぶ前後で、ゲーム内で出していない条件の結果を説明・予想できるか。
5. 自分のPCの例へ当てはめたときに、ゲームの比喩による新しい誤解が生まれていないか。

クリア率とプレイ時間だけでは、この到達目標を満たしたとは判定しない。短い録画、発話メモ、操作ログ、事前・事後の予想を対応させ、改善点を特定する。少人数の試作評価は問題の発見に使い、学習効果の一般的な実証結果としては扱わない。

## 最小構成と品質をさらに高める構成

### 最初の1本で必要な最小構成

- 実際のウィンドウをクリック・ドラッグ・キー入力できるcomputer use。
- 画面から独立した小さな学習モデルと、手計算等で確認した期待値。
- 問題ID・固定seedでやり直し、状態を読めて、一手ずつ進める検証窓口。
- 採用環境に合うUIテスト1系統。Swift/macOSならXCTest/XCUIAutomation、WebならPlaywright。
- 開始・途中・失敗・成功の画像と、代表的な1プレイの録画。
- 実機での性能計測と、想定する初心者による初見プレイ。

### 品質をさらに高める追加要素

- 入力記録をファイル化し、不具合から1コマずつ再生できるreplay。
- 画面・状態・エラー・計測値を同一試行IDでまとめる。
- 真理値表や境界条件、ランダム入力の広い確認。失敗した最小操作列を保存する。
- OS・画面サイズ・表示倍率・入力方法・文字サイズ等を固定した比較と、実配布環境での通し確認。
- 実時間のフレーム時間分布、長時間プレイでのメモリ増加、アイドル時の負荷を記録する。
- 回路表現や説明に対する技術レビューと、初心者の体験レビューを別々に実施する。

これらは追加の巨大ツールセットではなく、1本目のゲームの開発環境を少しずつ強くする方針である。すべてのテーマの実装を始める前に、代表的な1本で「実装→AIプレイ→再現→修正→人の理解確認」が回るかを確かめる。
