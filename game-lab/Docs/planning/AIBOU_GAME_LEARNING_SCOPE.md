# aibou — ゲーム化するハードウェア理解の範囲

作成日：2026-09-14  
位置づけ：リサーチ第1段階「何の理解をゲーム化すべきか」の初期案

## 1. 目的と前提

aibouのコンセプトは「エンターテインメント × ハードウェア理解」である。ゲームは独立したコア機能であり、遊ぶ楽しさと仕組みがわかる楽しさを提供する。もう一つのコア機能であるアクティビティモニタとつながり、学んだことを自分のPCの状態に重ねて理解できるようにする。

本書では、ゲーム化する対象を「部品名」から「発見してほしい仕組み・因果関係」まで具体化する。各テーマに、到達目標、体験で変えて比較する条件、調査優先度を付ける。想定する使用者は、日常的にPCを使うが内部の仕組みには詳しくない人である。

対象と優先順位は企画上の提案であり、学習効果や楽しさを実証した結果ではない。20テーマは20本のゲームを意味しない。1テーマを複数の小さな体験に分けたり、複数テーマを一つの体験につなげたりできる。

## 2. 何をゲーム化するかの判断基準

優先するのは、以下の性質を持つ理解である。

1. **後の理解につながる**：ほかの部品やPC全体を理解する土台になる。
2. **操作で因果を確かめられる**：入力、構成、容量、仕事量などを変えると、結果に意味のある違いが出る。
3. **試行錯誤を楽しめる可能性がある**：組み立てる、予想する、配分する、効率を工夫するなど、理解につながる選択がある。
4. **身近なPCの動作と結びつく**：起動、保存、同時作業、映像、発熱などを説明できるようになる。

知識の名称を覚えるだけで完結する内容は、展示の短い解説などに配置できる。遊びの中で条件を変える意味がある内容を、ゲーム化の中心に置く。楽しさの見込みは、次段階の既存ゲーム調査と試作で検証する。

## 3. 優先度の意味

- **A：最初に既存ゲーム調査へ進める**。回路から部品、部品からPC全体への理解をつなぐ8テーマ。
- **B：次に調査する**。部品ごとの特徴と日常の現象を広げる9テーマ。
- **C：深掘り候補として調査する**。物理的な成り立ちや機種ごとの構造に踏み込む3テーマ。

これは調査の優先順位であり、実装順・制作本数・使用者の受講順の確定ではない。特に面白い体験が見つかれば、B・Cのテーマも早期の試作候補にできる。モニタに表示されるかどうかだけでは順位を決めない。

H02「0・1」→ H03「論理・計算」→ H04「状態の保持」→ H05「命令実行」→ H06「RAMと保存」→ H01・H20「PC全体」

### 入口2：自分のPCの動きを知りたい

H01「PC全体の役割」→ H06・H07「作業場所と複数の仕事」→ H08〜H16の気になるテーマ → H20「全体の制約」

H01は最初に全体図を見る体験としても、学んだ部品をつなぎ直す体験としても使える。H20もCPUとメモリだけの小さな比較から始め、学習対象が増えるごとに広げられる。すべてを一列に並べ、前の展示を終えないと次に触れない構成には固定しない。

## 6. テーマの具体化例

### H06：RAMとストレージ

**中心となる問い**：「保存先に空きがあるのに、作業中の置き場所は足りなくなるのか？」

**習得してほしいこと**：作業中のデータと保存済みのデータを区別し、RAM容量とストレージ容量がそれぞれ何を制限するか説明できる。

**比較する条件**：架空のPCを使い、RAMと保存容量を別々に変更する。例えば、RAMが4枠・作業に必要なデータが6枠の状態で、保存容量だけを増やす場合とRAMを増やす場合を比較する。ここでの「枠」は体験用の単位であり、実機のアプリ数や容量に直接換算しない。

**理解を確かめる課題**：別の作業量・容量の組み合わせを初めて見せ、「どちらを変えると作業データをRAM内に収められるか」を予想し、理由を説明してもらう。保存せずに電源を切った場合と保存してから切った場合も区別できるか確かめる。

**モデルの範囲**：最初の体験では自動保存・圧縮・スワップ等を含めないことを示し、H10への入口を用意する。現実のPCでRAMが足りなくなると必ず即座に停止する、という説明にはしない。

**ゲーム化に向くと考える理由**：置き場所と保持する内容を選び、条件を変えた効果を確かめられる。具体的なルールや演出は次段階の調査を経て設計する。

### H03：論理回路

**中心となる問い**：「小さなON・OFFの仕組みをつなぐと、どうして計算できるのか？」

**習得してほしいこと**：入力から出力を予想し、複数の条件や1ビットの加算を回路で表現できる。

**比較する条件**：スイッチの状態、使う論理部品、接続方法を変える。まず一つの条件、次に複数条件、さらに和と桁上がりへ進む。

**理解を確かめる課題**：完成例と違う入力でも正しく動くか予想する。動かない回路を見て、目的に合うように接続を直せるか確かめる。

**ゲーム化に向くと考える理由**：組み立てる、動きを見る、失敗の理由を考えて直す、という試行錯誤が、そのまま理解につながる可能性がある。

### H20：PC全体とボトルネック

**中心となる問い**：「速いCPUにすれば、いつでも待ち時間は減るのか？」

**習得してほしいこと**：仕事を構成する各段階を追い、どの制約が全体に効いているかを考えられる。

**比較する条件**：計算、読み込み、保存などの所要時間を持つ単純化した仕事を用意し、まず一つの部品の条件だけを変える。次に別の仕事で同じ変更を試す。

**理解を確かめる課題**：初めて見る仕事で、効果がありそうな変更を選び、結果を予想する。結果が予想と違った場合に、次に見るべき場所を選べるか確かめる。

**実機との接続**：ゲーム内では条件を制御して因果を確かめる。実機では複数の要因が変化し得るため、観測値から原因候補を考える到達目標とし、モニタだけで必ず原因を特定できるとは教えない。

## 7. すべてのテーマで確かめる到達目標

| 観点 | 確かめ方 |
|---|---|
| 説明できる | 今回の結果について、関係する部品・データ・制約を使って説明してもらう |
| 予想できる | まだ試していない条件を提示し、実行前に結果と理由を答えてもらう |
| 応用できる | 数値や見た目が変わった課題、または身近なPCの場面で、同じ仕組みを使って判断してもらう |

文章回答だけを必須にせず、配置、接続、操作の選択でも理解を確かめられるようにする。試し続ければ偶然クリアできる課題だけでは、理解の確認として不十分である。楽しさと学習は別々に観察し、両方の成立を検証する。時間や合格点の数値基準は、試作段階で定める。

## 8. 調査・設計時に確認する誤解の候補

以下は今回ユーザー調査で確認した結果ではなく、表現が生まないよう確認したい誤解の候補である。

- CPU使用率の高さだけで、性能の高さや異常を判断する。
- RAMの使用量が多ければ、必ずメモリ不足だと考える。
- RAM容量、保存容量、帯域、遅延、計算速度を同じ「速さ」として扱う。
- コア数や周波数が2倍なら、どんな仕事も2倍速く終わると考える。
- GPUならすべての計算がCPUより速いと考える。
- CPU用RAMとGPU用RAMは、すべてのPCで別々に存在すると考える。
- 画面の更新頻度と、アプリが画像を生成する頻度を同一視する。
- 「熱い」「使用率が高い」「ファンが回る」を、それだけで故障と判断する。
- ゲーム内の比喩・数値・単純化したルールを、すべて実機の挙動に直接当てはめる。

CPUの使用状況は使用中・未使用の時間的な状態を読む入口となる。Appleはシステム・ユーザ・アイドルの区分を説明している。この観測の意味と、仕事が速いか・異常かという解釈を学習上も区別する。[Apple：CPUの動作状況](https://support.apple.com/ja-jp/guide/activity-monitor/actmntr43452/mac)

## 9. 現在のaibouとの対応

既存のモニタには、CPU、GPU、メモリ、ストレージ、電源・熱、ネットワーク、ディスプレイ、外部機器等の観測範囲がある。[現在のモニタの説明](https://github.com/SouD7/aibou/blob/0981d84/monitor/README.md)

H06〜H16・H18・H20は、その観測と接続しやすい。H02〜H05・H19は、直接の観測値がなくても独立したゲーム体験として価値を持つ。学習の対象は、現在取得できる数値の範囲に限定しない。

実機表示に接続する際は、取得できる量と学習モデル内の量を区別する。例えば、設定上の画面Hzは実際の描画FPSではなく、OSの熱状態はCPUの温度そのものではない。実際に取得できない値を、ゲーム内の数値から実測値として補わない。

本書は、この会話で合意した「ゲームとモニタの二つのコア機能」を前提とする。既存のハッカソン用要件文書は現在の実装背景を知る資料として参照し、今回のゲームの目的を狭める根拠にはしていない。

## 10. 次段階へ渡す単位

最初はAの8テーマについて、次の形式で既存ゲーム調査を行う。

**テーマID → 中心の問い → 習得してほしい理解 → 関連する既存ゲーム → 理解につながる操作・ルール → aibouで扱うための分割や単純化**

本書で既存ゲーム調査に渡せるのは、先頭の3項目と、比較する条件・到達目標である。作品の候補、採用するゲームの形式、制作本数、実装方法は、次段階で判断する。
